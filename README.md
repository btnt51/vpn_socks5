# VPN (SOCKS5-прокси)

Небольшой асинхронный SOCKS5-прокси-сервер на C++23. Сервер принимает TCP-подключения, соединяется с указанным клиентом узлом и передаёт трафик в обе стороны.

Сейчас поддерживаются:

- команда SOCKS5 `CONNECT`;
- IPv4, IPv6 и доменные имена;
- подключение без авторизации;
- раздельные журналы сервера и пользовательских сессий.

Команды `BIND`, `UDP ASSOCIATE` и авторизация по логину и паролю пока не поддерживаются.

## Требования

- CMake 3.20 или новее;
- компилятор с поддержкой C++23 (GCC 13+, Clang 16+ или актуальный Apple Clang);
- OpenSSL;
- Git и доступ в интернет при первой сборке.

Boost 1.90.0, fmt 11.2.0, spdlog 1.15.3 и GoogleTest 1.17.0 загружаются автоматически через CMake `FetchContent`.

### macOS

Установите Xcode Command Line Tools, CMake, Ninja и OpenSSL:

```bash
xcode-select --install
brew install cmake ninja openssl@3
```

Проект по умолчанию собирается для Apple Silicon (`arm64`).

### Ubuntu/Debian

```bash
sudo apt update
sudo apt install build-essential cmake ninja-build git libssl-dev
```

Проверьте, что установленный компилятор поддерживает C++23. В старых выпусках Ubuntu может потребоваться более новая версия GCC или Clang.

## Конфигурация

Приложение читает настройки из каталога `config` относительно текущей рабочей директории. Поэтому готовый бинарник следует запускать из корня репозитория.

### Сервер

Файл `config/server.json`:

```json
{
  "server": {
    "ip": "127.0.0.1",
    "port": 1080
  }
}
```

- `ip` — IPv4- или IPv6-адрес, на котором сервер принимает подключения;
- `port` — порт от `0` до `65535`.

Адрес `127.0.0.1` разрешает подключения только с локального компьютера. Чтобы принимать подключения со всех сетевых интерфейсов, укажите `0.0.0.0`. Не публикуйте прокси в интернет без авторизации, сетевого экрана и ограничения доступа по IP.

### Логирование

Файл `config/loggers.json`:

```json
{
  "log_directory": "./logs",
  "loggers": [
    {
      "module_name": "session",
      "filename": "session.log",
      "pattern": "[%Y-%m-%d %H:%M:%S.%e] [%n] [%t] [%l] %v",
      "level": "debug",
      "rotation_hour": 12,
      "rotation_minute": 5
    },
    {
      "module_name": "server",
      "filename": "server.log",
      "pattern": "[%Y-%m-%d %H:%M:%S.%e] [%n] [%t] [%l] %v",
      "level": "debug",
      "rotation_hour": 12,
      "rotation_minute": 5
    }
  ]
}
```

- `log_directory` — существующий каталог для журналов;
- `module_name` — уникальное имя модуля (`server` и `session` нужны приложению);
- `filename` — уникальное имя файла без пути;
- `pattern` — шаблон spdlog, содержащий `%v` или `%+`;
- `level` — один из уровней: `trace`, `debug`, `info`, `warning`, `error`;
- `rotation_hour` — час ежедневной ротации, от `0` до `23`;
- `rotation_minute` — минута ротации, от `0` до `59`.

Каталог из `log_directory` должен существовать до запуска:

```bash
mkdir -p logs
```

## Сборка

Из корня репозитория выполните:

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
```

Если Ninja не установлен, уберите параметр `-G Ninja`.

Для сборки без тестов добавьте `-DVPN_BUILD_TESTS=OFF` при конфигурации CMake:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DVPN_BUILD_TESTS=OFF
cmake --build build --parallel
```

## Запуск

Запускайте сервер из корня репозитория, чтобы он нашёл `./config`:

```bash
./build/vpn
```

При стандартной конфигурации SOCKS5-прокси будет доступен по адресу `127.0.0.1:1080`. Для остановки нажмите `Ctrl+C`.

## Проверка

В другом терминале выполните HTTP-запрос через прокси:

```bash
curl --proxy socks5h://127.0.0.1:1080 https://example.com
```

Префикс `socks5h` передаёт разрешение доменного имени прокси-серверу. Для проверки внешнего IP можно использовать:

```bash
curl --proxy socks5h://127.0.0.1:1080 https://api.ipify.org
```

## Тесты

Тесты собираются по умолчанию. После сборки запустите:

```bash
ctest --test-dir build --output-on-failure
```

## E2E- и нагрузочный тестер

Исполняемый файл `tester` запускает декларативно описанные сценарии через SOCKS5-прокси. Один и тот же runner используется как для E2E-проверок с небольшим количеством соединений, так и для продолжительного нагрузочного тестирования. Несколько сценариев запускаются параллельно.

Посмотреть доступные сценарии:

```bash
./build/tester/tester list
```

Сейчас определены:

- `pong` — короткоживущее соединение с обычным HTTPS-запросом и ответом;
- `interrupted-download` — продолжительное скачивание, во время которого HTTPS-эндпоинт закрывает соединение согласно сценарию;
- `complete-download` — полное скачивание файла размером 10 MiB с проверкой HTTP-статуса, `Content-Length` и фактически полученного размера.

Для конечного E2E-прогона задаются общее количество соединений и максимальная параллельность:

```text
--scenario <имя>:<количество соединений>:<параллельность>
```

Например, следующая команда запускает 100 соединений сценария `pong` с параллельностью 10 и одновременно 4 соединения `interrupted-download` с параллельностью 2:

```bash
./build/tester/tester run \
  --proxy-address 127.0.0.1 \
  --proxy-port 1080 \
  --scenario pong:100:10 \
  --scenario interrupted-download:4:2
```

Для нагрузочного тестирования указывается продолжительность измерения, а для каждого сценария — постоянная параллельность:

```text
--duration <время> --scenario <имя>:<параллельность>
```

Например:

```bash
./build/tester/tester run \
  --proxy-address 127.0.0.1 \
  --proxy-port 1080 \
  --duration 5m \
  --warmup 30s \
  --report-interval 1s \
  --rate 100 \
  --threads 4 \
  --source-address 127.0.0.2 \
  --source-address 127.0.0.3 \
  --scenario pong:200 \
  --scenario complete-download:20 \
  --scenario interrupted-download:20
```

Во время warm-up runner создаёт заданную нагрузку, но не включает завершившиеся соединения в итоговую статистику. Ограничение `--rate` действует с самого начала warm-up, поэтому прогрев не может исчерпать локальные сокеты до начала измерения. После warm-up нагрузка выполняется в течение `--duration`. Новые соединения перестают создаваться по окончании измерения или после `SIGINT`/`SIGTERM`, а уже запущенные соединения корректно завершаются.

Параметры:

- `--proxy-address` — адрес проверяемого SOCKS5-прокси, по умолчанию `127.0.0.1`;
- `--proxy-port` — порт SOCKS5-прокси, по умолчанию `1080`;
- `--source-address` — локальный IP для исходящих соединений tester-а; параметр можно повторять для формирования пула;
- `--duration` — продолжительность сбора статистики; поддерживаются суффиксы `ms`, `s`, `m` и `h`;
- `--rate` — глобальный предел новых соединений в секунду для суммы всех сценариев, включая warm-up;
- `--threads` — максимальное количество независимых сетевых потоков tester-а, по умолчанию `1`;
- `--warmup` — продолжительность прогрева, по умолчанию `0s`; используется только вместе с `--duration`;
- `--report-interval` — период вывода текущей статистики, по умолчанию `1s`;
- `--failure-backoff` — задержка перед повторной попыткой worker-а после ошибки клиента, по умолчанию `100ms`;
- `--scenario`, `-s` — сценарий и его нагрузка; параметр можно повторять для запуска разных сценариев.

Для команды `run` требуется хотя бы один `--scenario`. Количество соединений и параллельность должны быть больше нуля. Один и тот же сценарий нельзя указывать несколько раз.

Параллельность и rate регулируют разные свойства нагрузки. Число после имени сценария задаёт максимальное количество одновременно работающих клиентов этого сценария. `--rate` ограничивает суммарную скорость открытия новых соединений. Например, `pong:10` и `complete-download:20` дают до 30 активных клиентов, но при `--rate 100` tester начинает не более 100 новых соединений в секунду.

При `--threads N` runner разделяет concurrency и общий rate между независимыми shard-ами. У каждого shard-а собственные `io_context`, Cobalt executor, TLS context, HTTPS endpoint и локальные результаты. Сетевые объекты не используются одновременно из разных потоков. Runtime-статистика и итоговый отчёт агрегируются по всем shard-ам, поэтому `--rate 200 --threads 4` означает суммарно 200, а не 200 новых соединений на каждый поток. Если concurrency или rate меньше `N`, tester создаёт только необходимое количество потоков.

Если указан один или несколько `--source-address`, runner распределяет новые соединения по этому пулу round-robin. Перед подключением к SOCKS5 каждый клиент выполняет `bind(source-address, 0)`, где порт `0` поручает ОС выбрать свободный ephemeral-порт. Это позволяет использовать отдельное пространство локальных TCP-портов для каждого source IP и отодвигает `EADDRNOTAVAIL` при большом количестве короткоживущих соединений. Без `--source-address` локальный адрес и порт выбирает ОС, как и раньше.

На macOS адреса необходимо предварительно добавить на loopback-интерфейс:

```bash
sudo ifconfig lo0 alias 127.0.0.2 255.0.0.0
sudo ifconfig lo0 alias 127.0.0.3 255.0.0.0
sudo ifconfig lo0 alias 127.0.0.4 255.0.0.0
sudo ifconfig lo0 alias 127.0.0.5 255.0.0.0
```

Проверить настройку:

```bash
ifconfig lo0 | grep "inet "
```

Пример запуска с четырьмя source IP:

```bash
./build/tester/tester run \
  --proxy-address 127.0.0.1 \
  --proxy-port 1080 \
  --duration 5m \
  --warmup 30s \
  --report-interval 1s \
  --rate 600 \
  --threads 4 \
  --source-address 127.0.0.2 \
  --source-address 127.0.0.3 \
  --source-address 127.0.0.4 \
  --source-address 127.0.0.5 \
  --scenario pong:10 \
  --scenario complete-download:100 \
  --scenario interrupted-download:100
```

Ошибка `bind source address ...: Can't assign requested address` означает, что указанный IP не настроен на локальном интерфейсе. Ошибка `connect to proxy from ...: Can't assign requested address` означает, что для конкретного source IP не удалось выделить локальный TCP-порт. В обоих случаях прогон считается `INFRASTRUCTURE INVALID`.

Во время теста выводится агрегированная статистика за последний интервал:

```text
[00:01] active=240 completed=1842 succeeded=1842 failed=0 error-rate=0.0% rate=1842/s success-p95=18.0ms failure-p95=0.0ms tx=4.2MiB/s rx=94.0MiB/s errors=[none]
[00:02] active=240 completed=3743 succeeded=3741 failed=2 error-rate=0.1% rate=1901/s success-p95=24.0ms failure-p95=31.0ms tx=4.4MiB/s rx=91.0MiB/s errors=[io_error=2]
```

- `active` — текущее количество выполняющихся клиентов;
- `completed`, `succeeded`, `failed` и `error-rate` — накопительные значения после warm-up;
- `rate`, `success-p95`, `failure-p95`, `tx`, `rx` и `errors` — показатели за последний интервал;
- `success-p95` считается только по успешным клиентам, `failure-p95` — только по завершившимся с ошибкой;
- `errors` группирует ошибки текущего интервала по причине.

Для каждого шага сценария применяется `step_timeout`, а общее время клиента ограничивается `session_timeout`. Превышение лимита завершает текущую сетевую операцию и учитывается как ошибка `timeout`.

### SLO сценариев

В duration-based режиме итоговый `PASS` определяется SLO, декларативно заданным для каждого сценария:

| Сценарий | Максимальный error rate | Максимальный success-p95 | Максимальный success-p99 |
|---|---:|---:|---:|
| `pong` | 1% | 1500 ms | 2000 ms |
| `complete-download` | 1% | 3500 ms | 4500 ms |
| `interrupted-download` | 1% | 3500 ms | 4500 ms |

Сценарий проходит проверку, только если одновременно выполняются все три ограничения. Итоговый отчёт показывает фактические значения, лимиты и каждое нарушение:

```text
SLO FAIL error-rate=1.75%<=1.00% success-p95=2686.9ms<=3500ms success-p99=3029.8ms<=4500ms
  error-rate 1.75% exceeds 1.00%
```

Единичная допустимая ошибка больше не делает весь нагрузочный прогон неуспешным, если итоговый error rate остаётся в пределах SLO. В конечном E2E-режиме без `--duration` действует строгая проверка: любая ошибка означает `FAIL`.

`resource_exhausted` означает, что генератор нагрузки исчерпал локальный системный ресурс и больше не способен создавать корректную нагрузку. При первой такой ошибке tester немедленно прекращает запуск новых клиентов, дожидается уже запущенных и выводит `Tester result: INVALID`. Эта ошибка не включается в статистику сценария и не считается нарушением SLO приложения. Для остальных ошибок действует `--failure-backoff`, чтобы worker не создавал цикл из тысяч мгновенных повторов.

Полная справка:

```bash
./build/tester/tester --help
```

После завершения tester выводит агрегированную статистику по каждому сценарию: число успешных и неуспешных соединений, `success-p50`, `success-p90`, `success-p95`, `success-p99`, максимальную задержку успешных соединений, `failure-p95`, объём отправленных и полученных данных, а также ошибки, сгруппированные по причине. Для диагностики печатаются первые 20 ошибок отдельных клиентов.

Код возврата `0` означает успешное прохождение всех сценариев, `1` — нарушение SLO или ошибку сценария, `2` — некорректные аргументы командной строки, `3` — невалидный результат из-за ошибки тестовой инфраструктуры. При остановке сигналом возвращается `128 + номер сигнала`.

Агрегированные результаты базовой серии нагрузочных запусков находятся в [`tester/LOAD_TEST_RESULTS.md`](tester/LOAD_TEST_RESULTS.md).

## Частые ошибки

- `Failed to load config files` — запускайте бинарник из корня репозитория и проверьте наличие `config/server.json` и `config/loggers.json`.
- Ошибка про `log_directory` — создайте указанный каталог и проверьте путь в `config/loggers.json`.
- `Address already in use` — выбранный порт занят; измените `server.port` или остановите использующий его процесс.
- Ошибка OpenSSL при конфигурации — установите пакет OpenSSL для разработки (`libssl-dev` в Ubuntu/Debian или `openssl@3` в Homebrew).
- Ошибка загрузки зависимостей — первая конфигурация CMake требует доступа к GitHub.
